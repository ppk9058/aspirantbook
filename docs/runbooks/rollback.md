# Incident Recovery & Rollback Runbook

**Scope:** Production & Staging Disaster Recovery, Application Rollbacks, Database Restores  
**Platform:** AspirantBook (aspirantbook.com) on Render & PostgreSQL  
**Authority:** Platform Operations & Database Administration  

---

## 1. Rollback Principles & Guardrails

1. **Additive-Only Migrations:**  
   Database migrations in production are strictly forward-only and additive. Destructive operations (`DROP TABLE`, `DROP COLUMN`, altering types destructively) are forbidden in deploy migrations.
2. **Decoupled Application & Database Rollbacks:**  
   Code can be rolled back immediately on Render without touching the database schema, provided the schema changes adhere to the forward-only / additive policy.
3. **No Credential Exposure:**  
   Never log, output, or paste `DATABASE_URL`, `DIRECT_URL`, or secret access keys into chat, ticketing systems, or build logs.

## 2. Application Rollback on Render

Render maintains full history of previously deployed Docker container images.

### Procedure (Estimated Time: < 2 minutes):
1. Navigate to the **Render Dashboard** → Select the `trillionskill` web service.
2. Open the **Events** tab.
3. Locate the last known good deploy event.
4. Click the three dots (`...`) on that deploy and select **Rollback to this deploy**.
5. Render will launch a new instance running the prior immutable container image.
6. The container health check (`/api/health`) gates traffic switching; incoming traffic is routed to the previous version once healthy.
7. Verify functionality with `BASE_URL=https://aspirantbook.com scripts/ops/staging-smoke.sh`.

## 3. Database Disaster Recovery & Restore Steps

When data corruption or catastrophic failure requires point-in-time recovery from a backup dump.

### Backup Retention & Storage
- Backups are generated by `scripts/ops/db-backup-to-s3.sh` and stored in S3/R2 under `s3://$BUCKET/backups/db_backup_<timestamp>.dump`.
- Pre-deploy automated verification is executed using `scripts/ops/backup-restore-test.sh`.

### Restore Procedure:
1. **Download Backup Dump from S3/R2:**
   ```bash
   aws s3 cp s3://$S3_BUCKET/backups/db_backup_<YYYYMMDD_HHMMSS>.dump /tmp/restore.dump
   ```
2. **Verify Restore in Isolated Throwaway Database:**
   ```bash
   SOURCE_URL="$DIRECT_URL" scripts/ops/backup-restore-test.sh
   ```
   *Ensures pg_restore succeeds and row counts match before touching live instances.*
3. **Target Database Restore via pg_restore:**
   ```bash
   pg_restore --clean --if-exists --no-owner --no-acl --exit-on-error \
     --dbname="$DIRECT_URL" /tmp/restore.dump
   ```
4. **Post-Restore Verification:**
   - Execute row count checks: `psql "$DIRECT_URL" -f scripts/ops/db-size-report.sql`.
   - Run health check: `curl -H "x-health-details-token: $HEALTH_DETAILS_TOKEN" https://aspirantbook.com/api/health`.

## 4. Migration Rollback Policy

- **Why Forward-Only?**
  Running `prisma migrate down` or dropping columns in a shared production database can lead to data loss and breaks zero-downtime rolling deploys.
- **Rollback Procedure for Problematic Migrations:**
  1. Do NOT delete migration files or drop columns manually.
  2. Author a new additive fix migration that reverses the logical change (e.g. recreating a constraint, relaxing a validation, or adding an index).
  3. Deploy the fix via `scripts/ops/migrate-deploy.sh`.

## 5. Who-Does-What Incident Checklist

| Role | Responsibilities | Action Items |
| :--- | :--- | :--- |
| **Incident Commander (Lead)** | Coordinates response, communicates status | 1. Declare incident severity.<br>2. Authorize application rollback or restore.<br>3. Monitor customer support channels. |
| **Infrastructure Lead** | Render & Cloudflare management | 1. Execute application rollback via Render Events tab.<br>2. Check container boot logs for security refusals.<br>3. Verify Cloudflare edge routing and SSL mode. |
| **Database Administrator (DBA)** | PostgreSQL integrity & restores | 1. Identify valid backup timestamp in S3/R2.<br>2. Run `backup-restore-test.sh` on isolated test target.<br>3. Execute `pg_restore` if catastrophic failure confirmed.<br>4. Run `db-size-report.sql` to verify table row counts. |
| **QA / Verification Engineer** | Functional smoke testing | 1. Run `scripts/ops/staging-smoke.sh`.<br>2. Validate public pages, auth endpoints, and health status.<br>3. Verify payment webhook idempotency. |
